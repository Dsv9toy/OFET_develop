# Как устроена связь ПК и платы по Ethernet: от кнопки до проводов

Документ отвечает на вопрос «что на самом деле происходит, когда программа подключается, отправляет команду и ждёт ответ». Сначала общая картина (уровни), затем путь одной команды `PING` по байтам, затем что делает Windows, что делает Qt, что делает наш код, и как то же самое будет сделано на плате STM32.

---

## 1. Уровни: кто за что отвечает

Связь построена «слоями». Каждый слой решает одну задачу и пользуется слоем ниже, не вникая в его устройство.

| Уровень | Задача | Чем адресует | Где реализован на ПК | Где реализован на плате |
|---|---|---|---|---|
| 5. Наш протокол | смысл: команды `PING`, `TRANS;...`, ответы `DATA;...` | | **наш код**: `DeviceClient`, `MainWindow` | **наш код**: `ofet_core` |
| 4. TCP | надёжная доставка потока байтов: без потерь, по порядку | порт (5000) | Windows (драйвер `tcpip.sys`) | библиотека LwIP |
| 3. IP | доставка пакета до нужного компьютера в сети | IP-адрес (192.168.1.10) | Windows | LwIP |
| 2. Ethernet (MAC) | передача кадра до соседнего устройства по кабелю | MAC-адрес (00:80:E1:00:00:00) | сетевая карта и её драйвер | модуль ETH внутри STM32 + драйвер HAL |
| 1. Физический | превращение битов в электрические сигналы в кабеле | | микросхема PHY сетевой карты | микросхема PHY LAN8710A на плате |

Главное: **наш код работает только на верхнем уровне 5.** Он передаёт системе строку `PING\n` и получает от неё строку `PONG\n`. Всё, что ниже (как разбить на пакеты, куда отправить, что делать при потере пакета, как закодировать биты в кабеле), делают Windows на ПК и библиотека LwIP на плате. Это сделано специально: протоколы TCP/IP очень сложные, и писать их самому незачем, они давно отлажены.

Qt в этой схеме это «переходник» между нашим кодом и Windows: класс `QTcpSocket` вызывает функции Windows для работы с сетью (они называются Winsock) и сообщает нам о событиях сигналами.

## 2. Путь одной команды PING по байтам

Пусть ПК имеет адрес 192.168.1.1, плата 192.168.1.10, соединение уже установлено.

### 2.1 Наш уровень

Программа вызывает `m_dev.send("PING")`. В `DeviceClient::sendLine()`:

```cpp
m_sock.write(line.toLatin1() + '\n');
```

В сокет уходят 5 байтов (в шестнадцатеричном виде):

```
50 49 4E 47 0A
 P  I  N  G  \n
```

На этом работа нашего кода закончена: `write()` только кладёт байты в буфер отправки и сразу возвращается, не дожидаясь, пока они дойдут.

### 2.2 TCP добавляет свой заголовок (20 байтов)

| Поле | Значение | Смысл |
|---|---|---|
| Порт отправителя | например 51734 | Windows выбрала свободный порт для этого соединения при подключении |
| Порт получателя | 5000 | порт сервера на плате |
| Номер последовательности | например 1001 | номер первого байта этого куска в общем потоке |
| Номер подтверждения | | сколько байтов от платы ПК уже получил |
| Флаги | PSH, ACK | «передай данные программе сразу», «в поле подтверждения верное число» |
| Окно | | сколько ещё байтов ПК готов принять |
| Контрольная сумма | | проверка, что данные не испорчены |

### 2.3 IP добавляет свой заголовок (20 байтов)

| Поле | Значение |
|---|---|
| Адрес отправителя | 192.168.1.1 |
| Адрес получателя | 192.168.1.10 |
| Протокол | 6 (это TCP) |
| Время жизни (TTL) | 128 |
| Длина, контрольная сумма заголовка | |

### 2.4 Ethernet добавляет заголовок (14 байтов) и контрольную сумму (4 байта)

| Поле | Значение |
|---|---|
| MAC получателя | MAC платы, например 00:80:E1:00:00:00 |
| MAC отправителя | MAC сетевой карты ПК |
| Тип | 0x0800 (внутри IP) |
| ... данные (IP + TCP + 5 байтов) ... | |
| FCS | контрольная сумма всего кадра, считает сетевая карта |

Итого 14 + 20 + 20 + 5 = 59 байтов. Минимальная длина кадра Ethernet 60 байтов без FCS, поэтому карта добавит 1 байт-заполнитель. Пять полезных байтов едут в кадре из 64.

**Откуда ПК знает MAC платы?** Протокол **ARP**. Перед первой отправкой на 192.168.1.10 Windows рассылает всем в сети кадр «у кого адрес 192.168.1.10? ответьте на MAC такой-то». Плата отвечает своим MAC, Windows запоминает пару «IP - MAC» на несколько минут (список можно посмотреть командой `arp -a`).

### 2.5 Физический уровень

Сетевая карта отдаёт кадр микросхеме PHY, та кодирует биты в напряжения на парах проводов кабеля (100 Мбит/с, кодирование MLT-3, по одной паре в каждую сторону). На плате PHY LAN8710A принимает сигнал, восстанавливает биты и передаёт их в МК по интерфейсу RMII: 2 бита за такт 50 МГц от генератора ASV-50.000MHZ.

### 2.6 Обратный путь

На плате всё происходит в обратном порядке: модуль ETH проверяет FCS и MAC получателя, LwIP снимает заголовки IP и TCP, проверяет контрольные суммы, отправляет ПК подтверждение (ACK) и отдаёт нашему коду 5 байтов `PING\n`. Наш код отвечает `PONG\n`, и тот же путь повторяется в сторону ПК.

## 3. Как устанавливается соединение (кнопка «Подключиться»)

`QTcpSocket::connectToHost("192.168.1.10", 5000)` запускает так называемое **тройное рукопожатие** TCP:

```
ПК                                   Плата
 |  SYN (хочу соединиться, мой номер X)  |
 | ------------------------------------> |
 |  SYN+ACK (согласна, мой номер Y,      |
 |           жду от тебя X+1)            |
 | <------------------------------------ |
 |  ACK (жду от тебя Y+1)                |
 | ------------------------------------> |
 |        соединение установлено         |
```

Номера X и Y нужны, чтобы обе стороны могли пересчитывать байты: каждая сторона подтверждает, сколько байтов получила, и если подтверждение не пришло за отведённое время, TCP сам **повторяет отправку**. Поэтому наш код никогда не видит потерянных или переставленных байтов.

Если на плате никто не слушает порт 5000, она ответит кадром RST («отказано»), и Qt выдаст ошибку «Connection refused». Если плата вообще не отвечает (выключена, не та сеть), Windows несколько раз повторит SYN и примерно через 20 с выдаст ошибку «таймаут подключения».

Закрытие соединения: обмен кадрами FIN и ACK в обе стороны. При выдёргивании кабеля никаких FIN не приходит: TCP узнаёт об обрыве только тогда, когда его отправки перестают подтверждаться. Именно поэтому у нас есть собственные PING и таймауты (раздел 5.3).

**Поиск платы** использует UDP, а не TCP. UDP не устанавливает соединение и ничего не подтверждает: просто отправляет один пакет. Запрос `DISCOVER` отправляется на широковещательный адрес 192.168.1.255, которому соответствует MAC FF:FF:FF:FF:FF:FF, то есть «всем». Такой кадр принимают все устройства сети, а отвечает только плата.

## 4. Как программа «ждёт», не занимая процессор

### 4.1 Цикл событий

Программа не крутится в цикле «пришли ли данные? пришли ли данные?». Она почти всё время **спит** внутри функции `app.exec()` (`main.cpp`). Внутри неё Qt вызывает функцию Windows ожидания сообщений (`MsgWaitForMultipleObjectsEx`). Поток программы останавливается, процессор не расходуется, пока не произойдёт одно из событий:
- пользователь нажал кнопку или сдвинул мышь;
- сработал таймер;
- **в сокете что-то произошло**: соединение установлено, пришли данные, соединение закрыто.

Когда событие случилось, Windows будит поток, Qt выясняет, что произошло, и вызывает нужную функцию. Эта функция быстро отрабатывает и возвращается, и программа снова засыпает.

### 4.2 Как Windows сообщает Qt о данных в сокете

1. При создании сокета Qt переводит его в **неблокирующий режим** (функция Winsock `ioctlsocket(FIONBIO)`). Это значит, что вызовы «прочитать» и «подключиться» никогда не останавливают программу: если данных нет, они сразу возвращают «пока ничего».
2. Qt просит Windows: «когда у этого сокета будут данные для чтения, место для записи, подключение или закрытие, пришли сообщение моему скрытому служебному окну» (функция `WSAAsyncSelect`).
3. Пришёл кадр из сети: сетевая карта вызывает прерывание, драйвер забирает кадр, стек TCP/IP Windows (`tcpip.sys`) разбирает заголовки, отправляет ACK и кладёт 5 байтов в **приёмный буфер сокета** в памяти Windows. Затем посылает сообщение служебному окну Qt.
4. Цикл событий получает это сообщение, Qt читает байты из буфера Windows в свой буфер и испускает сигнал `readyRead`.
5. К `readyRead` подключена наша функция `DeviceClient::onReadyRead()`.

Всё это (пункты 1-4) спрятано внутри Qt. Наш код видит только сигналы: `connected`, `readyRead`, `disconnected`, `errorOccurred`.

### 4.3 Таймеры

`QTimer` устроен так же: Qt просит Windows прислать сообщение через заданное время (функция `SetTimer`), и цикл событий вызывает подключённую функцию. Пока таймер «тикает», программа ничего не делает и не тратит процессор.

## 5. Наш код: класс DeviceClient построчно

Файл `src/deviceclient.cpp`. Это весь «наш» сетевой код на ПК.

### 5.1 Подключение и события

```cpp
connect(&m_sock, &QTcpSocket::connected,    this, [this] { ... emit connected(); });
connect(&m_sock, &QTcpSocket::disconnected, this, [this] { ... emit disconnected(); });
connect(&m_sock, &QTcpSocket::readyRead,    this, &DeviceClient::onReadyRead);
connect(&m_sock, &QTcpSocket::errorOccurred, this, [this](...) { emit errorText(m_sock.errorString()); });

void DeviceClient::connectToDevice(const QString &host, quint16 port)
{
    m_sock.abort();                    // закрыть старое соединение, если было
    m_sock.connectToHost(host, port);  // начать подключение и сразу вернуться
}
```

`connectToHost` не ждёт окончания рукопожатия: она только запускает его. Через некоторое время придёт либо сигнал `connected` (успех), либо `errorOccurred` (отказ, таймаут). `MainWindow` подключён к этим сигналам и меняет индикатор.

### 5.2 Приём: TCP это поток, а не сообщения

Важная особенность TCP: он передаёт **поток байтов**, а не отдельные сообщения. Если плата отправит две строки `DATA;1;...\n` и `DATA;2;...\n`, к нам они могут прийти:
- двумя кусками, как отправлены;
- одним куском, склеенными;
- тремя кусками, причём одна строка разрезана посередине.

Поэтому каждая наша строка заканчивается символом `\n` (LF), и `onReadyRead()` собирает байты в буфер и вырезает из него только **целые** строки:

```cpp
void DeviceClient::onReadyRead()
{
    m_rx += m_sock.readAll();                    // дописать всё, что пришло, в конец буфера
    int pos;
    while ((pos = m_rx.indexOf('\n')) >= 0) {    // пока в буфере есть целая строка
        QString line = QString::fromLatin1(m_rx.left(pos)).trimmed();
        m_rx.remove(0, pos + 1);                 // убрать её из буфера вместе с \n
        ...
        emit lineReceived(line, line.split(';'));   // отдать строку окну, уже разбитую по ';'
    }
    // хвост без \n остаётся в m_rx до следующего readyRead
}
```

### 5.3 Таймаут ответа и автоматический PING

TCP гарантирует доставку, но не говорит, жива ли плата: при выдернутом кабеле соединение ещё долго считается открытым. Поэтому поверх TCP сделаны свои проверки:

```cpp
void DeviceClient::sendLine(const QString &line, bool silent)
{
    m_sock.write(line.toLatin1() + '\n');
    m_waitReply = true;
    m_watchdog.start();       // через 2000 мс сработает onWatchdog(), если ответа не будет
    m_keepAlive.start();      // отсчёт 3 с до следующего автоматического PING начинается заново
}
```

- **Сторож `m_watchdog`** (2 с, однократный): любая принятая строка его останавливает. Не остановлен вовремя, значит, плата не ответила: испускается `timeout()`, окно пишет «Нет ответа» и красит индикатор. Во время измерения сторож перезапускается на каждую строку, потому что плата шлёт `PROG` не реже раза в 0,5 с.
- **Таймер `m_keepAlive`** (3 с, повторяющийся): если программа ничего не отправляла 3 с, `onKeepAlive()` шлёт `PING` (без записи в журнал). Это нужно плате: она снимает напряжения, если от ПК 10 с не пришло ни одной строки.

### 5.4 Что делает программа в целом (последовательность)

```
Нажата «Подключиться»
  -> DeviceClient::connectToDevice()         запуск рукопожатия, возврат сразу
  ... цикл событий спит ...
  <- сигнал connected                         Windows: рукопожатие завершено
  -> MainWindow::onConnected()               индикатор зелёный, send("STAT?")
  ... спит ...
  <- сигнал readyRead                         пришли байты "STAT;IDLE;1.6484;0;1;1\n"
  -> DeviceClient::onReadyRead()             вырезана строка
  -> MainWindow::onLine()                     показаны Uсм, транзистор, диапазон
  ... спит ...
  <- таймер keepAlive (3 с)                  -> send("PING")
  <- readyRead "PONG\n"                       сторож остановлен
  ...
```

## 6. То же на плате STM32 (будет в прошивке)

На плате нет Windows, поэтому уровни 3 и 4 (IP, TCP, UDP, ARP, DHCP) реализует библиотека **LwIP** (lightweight IP), которую подключает CubeMX. Уровни 1 и 2 реализуют PHY LAN8710A и модуль ETH внутри STM32.

1. **Приём кадра.** Модуль ETH сам, без участия процессора (через встроенный DMA), складывает пришедший кадр в буфер в оперативной памяти и вызывает прерывание.
2. **Главный цикл** прошивки (без операционной системы):
   ```c
   while (1) {
       MX_LWIP_Process();   // забрать принятые кадры, обработать ARP/IP/TCP/DHCP, таймеры TCP
       app_poll();          // наша логика: автоматы развёртки, реле, измерения
   }
   ```
   `MX_LWIP_Process()` вызывает `ethernetif_input()` (забирает кадр у драйвера) и `sys_check_timeouts()` (повторы отправки, таймеры DHCP и ARP).
3. **TCP-сервер.** При старте прошивка создаёт «слушающий» сокет LwIP на порту 5000 (`tcp_new()`, `tcp_bind(.., 5000)`, `tcp_listen()`) и регистрирует свои функции-обработчики:
   - `tcp_accept`: ПК подключился -> `app_on_connect()`;
   - `tcp_recv`: пришли байты -> наш код так же собирает их в буфер, вырезает строки по `\n` и передаёт каждую в `app_on_line()`;
   - `tcp_err` или пустой приём: соединение закрыто -> `app_on_disconnect()` (напряжения снимаются).
4. **Отправка.** `hw_send_line()` вызывает `tcp_write()` (положить байты в буфер отправки LwIP) и `tcp_output()` (отправить сейчас). Повторы при потерях, подтверждения и окно LwIP делает сам.
5. **DHCP.** `dhcp_start()` при включении; если за 5 с адрес не получен, прошивка задаёт `192.168.1.10` функцией `netif_set_addr()`.
6. **Поиск.** UDP-сокет на порту 5001 (`udp_new()`, `udp_bind()`, `udp_recv()`): на строку `DISCOVER` прошивка отвечает `OFET;<IP>;5000` на адрес и порт отправителя (`udp_sendto()`).

Принцип тот же, что на ПК: никаких ожиданий в цикле, только реакция на события (пришли байты, сработал таймер). Поэтому плата может одновременно вести развёртку, считать паузы реле и отвечать на `STOP`.

## 7. Как увидеть всё это своими глазами

Программа **Wireshark** (бесплатная, wireshark.org) показывает все кадры, проходящие через сетевую карту ПК, с разбором по уровням.

1. Установить Wireshark, запустить, выбрать сетевой адаптер, к которому подключена плата (для эмулятора на этом же ПК: «Adapter for loopback traffic capture»).
2. В строке фильтра ввести `tcp.port == 5000 || udp.port == 5001` и нажать Enter.
3. В программе нажать «Подключиться» и «Проверка связи».

Будут видны: рукопожатие (SYN, SYN-ACK, ACK), кадры с данными `PING` и `PONG`, подтверждения ACK, запрос `DISCOVER` и ответ платы. Щелчок по кадру раскрывает все заголовки из раздела 2: MAC-адреса, IP-адреса, порты, номера последовательности, а внизу видны сами байты `50 49 4E 47 0A`.

Ещё полезные команды Windows (в `cmd`):
- `ping 192.168.1.10`: отвечает ли плата на уровне IP (протокол ICMP, его на плате обрабатывает LwIP);
- `arp -a`: таблица соответствия IP и MAC;
- `netstat -an | findstr 5000`: открытые соединения на порту 5000 и их состояние (`ESTABLISHED` = соединение установлено).
